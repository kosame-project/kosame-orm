# Drizzle互換 Model型ORM 要件洗い出し

作成日: 2026-08-25 / 更新: 2026-09-01
ステータス: 上から順に検討中。決まったものは「決定事項」に移し、未決定分は各章に残す。

## 0. 背景（本人の発言メモ）

- 個人利用目的で、他人に使わせる想定は特にない
- Honoユーザーが増えてきている流れの中で、PrismaかDrizzleかとなった場合、SQLライクな書き方・パフォーマンスの面でDrizzleの方がいいと感じている
- ただしDrizzleはEF Core（ASP.NET Core）と比べると「Model」の概念がなく、何も決まっていない感じがある
- 自分自身はEF Coreを触ってきた経験があり、そこで馴染んだModel的な秩序をDrizzleにも持たせたい、というのが動機
- 大規模から小規模までカバーできるものにしたい

## 全体を貫く原則

- **Drizzleは最終的な永続化エンジンとして扱う**。DB接続・SQL実行・マイグレーションといった「実行」に徹してもらい、Model定義・アソシエーション・DbContext相当の概念など、ORMとしての意味づけはすべてModel層側が主として持つ。個々の論点で迷ったら「これはModel層の責務か、drizzle(永続化エンジン)の責務か」で判断する
- **明示性を優先する**: 暗黙的な魔法（ambient/グローバルな状態、実行時まで形が決まらないProxy、自動Change Tracking等）より、明示的に紐付ける・書く設計を優先する。これまでの決定（`relations()`に頼らずModel層で明示定義、db.queryの糖衣に頼らずリレーションごとの明示的なクエリ+アプリ側hydration、Proxy不使用、自動Change Tracking不採用）と一貫させる

## 決定事項(ここまでで決まったこと)

- **プロジェクト名**: `kosame`（小雨）に決定
  - **経緯**: downpour / pour / Entity-drizzle / model-framework / spitting / shower decode / Henkanなど複数候補を検討。downpour・pour・henkanはnpmで既存の無関係パッケージに取られておりそのままでは使えないことが判明。spittingは英語圏で唾を吐くイメージが先に立つ懸念、shower decodeは「decode」の部分が実際のORMの役割（hydrate）と結びつきが弱い懸念があった
  - **理由**: kosameはdrizzle（英語で小雨・霧雨）をそのまま日本語に訳した語で、雨の強さで対比を作るのではなく「drizzleと同じ強さの雨を日本語で呼び直す」形になっており、「drizzleの上に被せるレイヤー」という立ち位置と自然に馴染む。Hono・Jotaiなど日本語名のJS OSSライブラリの前例があり、発音のしやすさ（シンプルな音の並び）の面でも違和感がない
  - **npm確認**: `kosame`はnpmで未使用（2026-09-01時点）
- **アーキテクチャ方針**: drizzle-ormをラップし、その上にModelレイヤーを被せる方式にする
  - **drizzle側の役割**: migration、SQL生成、実際のCRUD（INSERT/UPDATE/DELETE/SELECT）の実行 = 永続化エンジン
  - **Model層（自作）側の役割**: ユーザー向けのModel API（`user.save()`等）を、内部でdrizzleのINSERT/UPDATE/DELETE呼び出しに変換する「翻訳層」として動く。Model定義そのもの、アソシエーション定義、DbContext相当の機能も持つ
  - **理由**: 実装コストが低く軽量に作れる、かつDrizzleとの互換性も保てる。CRUDの実行自体をdrizzleに委譲するので、drizzleの型推論（`InferInsertModel`等）をModel APIの引数型としてほぼそのまま流用でき、型を自前で作り直すコストを抑えられる見込み
- **リレーションの定義場所**: アソシエーション（`hasMany`/`belongsTo`相当）はModel層側で定義し、それをdrizzleへの呼び出しに変換する。drizzleの`relations()`ヘルパーをアソシエーションの一次情報にはしない
- **リレーションの変換先**: drizzleの`db.query`（relational query API, `with:{...}`）にもJOINにも頼らず、親のキー配列を`IN`句にしたクエリをリレーションごとに1本発行し、アプリケーション側で親キーごとにgroupByしてhydrateする方式（バッチクエリ方式）を採用
  - **経緯**: 当初はselect+join方式を検討していたが、better-drizzleの実装調査（6章参照）で、この方式ならJOINを一切使わずにN+1を回避しつつ、fan-out（直積）問題も原理的に起きないことが分かり、こちらに変更した
  - **理由**: `db.query`は`relations()`定義への依存が発生し、「アソシエーションの一次情報はModel層」という決定と相性が悪い。バッチクエリ方式なら`relations()`にもJOINのカラム衝突にも依存せず完結し、「永続化エンジンに徹してもらう」という全体原則にも忠実
  - **better-drizzleとの差別化**: クエリ戦略自体はbetter-drizzleと重なる部分が大きいが、差別化はクラスベース＋インスタンスメソッド＋DbContext的なAPI表面（決定済み）ですでに十分確保できている、と整理して結論づけた。クエリの内部実装がどう動くかはユーザーからは直接見えない部分であり、書き味の違いの方が本質的な差別化になる。drizzle自体に対してユーザーが設定する項目数を減らす方向性は、差別化のためではなく、独立した使いやすさ向上のアイデアとして扱う（具体化は決定事項「drizzle初期化時の設定項目の削減」参照。schema/casing/loggerデフォルト値まで決定済み）
- **DbContext的 vs ActiveRecord的**: DbContext的（コンテキスト/セッションオブジェクト経由でModel操作を行う）方式を採用
  - **理由**: 小規模〜大規模まで幅広くカバーしたい、という方針に対してDbContext的な設計の方が向く（後述のユーザー像調査とも整合）。また、drizzleの`db.transaction(async (tx) => {...})`というコールバック型のトランザクションAPIとも、コンテキスト/セッション経由の設計は自然に噛み合う（トランザクションの通し方という別の未決定事項も解決しやすくなる）
  - ActiveRecord的な「Modelクラスが直接グローバルなdrizzle接続を参照する」形は書く量が少なく個人利用では手軽だが、複数コンテキスト（マルチテナント、テストごとの独立接続など）やトランザクションの配線がやりにくく、大規模用途との両立が難しいため見送り
- **インスタンスメソッドの有無**: コンテキスト経由のCRUD（`context.users.find()`等）に加えて、`user.save()`のようなインスタンスメソッドも持たせる方針を採用（better-drizzleのようなリポジトリ関数のみの形にはしない）
- **Model定義方式**: クラスベース（`class User extends Model {...}`）を採用。関数/ファクトリベース、コード生成（codegen）は見送り
  - **理由**: インスタンスメソッド（`user.save()`等）との相性が良く、コンテキスト/トランザクションへの参照もprivateフィールド（`#context`等）として自然に持たせられる。継承・Mixin（2章の未決定項目）ともクラスの仕組みがそのまま使える。codegenは実装コストが一番高くつくため見送り（「実装コストを抑える」という全体方針に反する）
  - **better-drizzleとの違いとして意図的に選択**: better-drizzleは関数/ファクトリベース（`0 codegen`のリポジトリスタイル）。今回はインスタンスメソッドを持たせる方針のため、あえてクラスベースを選ぶ
  - **付随する決定**: Modelインスタンスはユーザーが直接`new User()`する想定ではなく、コンテキスト側のファクトリメソッド（`context.users.find()`等）経由でのみ生成する（コンテキスト未設定のインスタンスができないようにするため）
  - **Proxyは使わない**: コンテキストの`context.users` / `context.posts`のようなテーブルごとの入り口は、スキーマが起動時に判明している以上、Proxyで動的に生やす必要はなく、スキーマをiterateして起動時に一度組み立てる方式で十分（実装・デバッグの単純さ、型推論の素直さを優先）
- **コンテキスト/トランザクション参照の持たせ方**: 明示的な方式（コンストラクタ注入）を採用。AsyncLocalStorage等によるambient（暗黙的な現在コンテキストの追跡）は不採用
  - **仕組み**: コンテキスト側のファクトリメソッドがModelインスタンスを生成する際、自分自身（またはdrizzleの`db`/`tx`ハンドル）をコンストラクタ経由でprivateフィールド（`#context`）に注入する。インスタンスは生成された瞬間からずっとそのコンテキスト/トランザクションを覚えている
  - **理由**: 「明示性を優先する」という全体原則と一貫する。ambient方式は書き味は自然になるが、スコープを抜けた後に呼び出した場合の挙動が曖昧になりやすく、暗黙的な魔法が増える。実装コストもexplicit方式の方が低い
  - **非目標として明記**: EF Coreの`Attach()`のような「生成後に別のコンテキスト/トランザクションへ後から紐付け直す」機能は持たない。Modelインスタンスは生成時のコンテキストに固定
- **対応DB**: PostgreSQL・MySQL・SQLiteの3つに対応する方針
  - **理由**: Postgres・MySQLは素直に欲しい。SQLiteは単体DBとしてだけでなく、Cloudflare D1（SQLite互換）を使う層のニーズも見込んで対応する
- **対応ホスティング/デプロイ環境**: Railwayのような、標準的なNode.jsプロセス＋TCP接続でPostgres/MySQLに繋ぐ一般的なホスティング環境も対応範囲に含める
  - **理由**: 本人が普段Railway（Postgres含む）でAPIをデプロイしている実績があり、そこで問題なく動くことを前提にする。Cloudflare D1のようなHTTP/fetchベースの接続方式と、Railwayのような標準TCP接続方式の両方をドライバレベルで支えられるようにする必要がある（1章のドライバ互換性の詳細に影響）
- **EF Coreからの移植範囲**: 以下の形で整理して決定
  - **すでに移植済み/対応済みとして扱えるもの**: DbContext（DbContext的方式）、DbSet<T>（`context.users`等の入り口）、ナビゲーションプロパティ＋`.Include()`（Model層のアソシエーション定義＋バッチクエリ変換）、マイグレーション（drizzle-kitへ委譲）、Fluent API/Data Annotationsによるスキーマ設定（drizzleの`pgTable`側がすでに担うため、Model層に別のスキーマ設定DSLは持たせない）
  - **移植しないと決定**: 遅延ロード（Lazy Loading、プロパティアクセス時の動的プロキシによる自動取得）。Proxy不使用の方針と矛盾するため非対応。関連データが必要なら明示的なeager loadingのみに統一
  - **移植しないと決定**: 自動Change Tracking＋`context.saveChanges()`による複数エンティティの一括保存（Unit of Work）。すでに決定済みの「`user.save()`は呼んだ瞬間にdrizzleへ即時反映される」設計と両立せず、「明示性を優先する」原則にも反するため不採用。各Modelインスタンスの変更は`.save()`等の明示呼び出しでのみ反映される
  - **決定済み**: 楽観的排他制御（RowVersion的な同時更新検知）は個人利用では優先度低く見送り（詳細・代替案は7章参照）。グローバルクエリフィルタ（ソフトデリート自動除外）はSoftDeletable mixinの一部として決定済み。SaveChanges Interceptorは2章の「フック」項目でカバー済み
- **リレーションのネスト対応範囲・hydration設計**: 以下の形で整理して決定
  - **ネストは1段階まで（あえて維持）**: JOINをやめてバッチクエリ方式に変えたことで、技術的には多段ネストも同じロジックの再帰適用で対応できるようになったが、初期の実装スコープを絞るため「1段階まで」の制約はあえて残す。`User → Posts`のような直接の関連までを対応範囲とし、`User → Posts → Comments`のような孫関連の同時eager loadingは初期スコープ外（将来課題）
  - **直積（カルテジアン積）は原理的に非発生**: JOINを使わないため、複数のhasMany系関連を同時にeager loadしてもfan-out（親カラム重複）は起きない。リレーションごとに、親キー配列を`IN`句にした別クエリを1本発行してアプリケーション側でマージする
  - **hydrationアルゴリズムは統一**: hasMany/多対多の結果は「親の主キーでgroupByし、子の配列にまとめる」という単純なロジックに統一する
- **コンストラクタの非公開/制限方法**: 「モジュール外にエクスポートしない`Symbol`をコンストラクタの必須引数（ブランド）として要求する」方式を採用
  - **仕組み**: `const INTERNAL = Symbol("internal-only")`をModel定義モジュール内だけに閉じて持ち、コンストラクタの必須引数として`brand: typeof INTERNAL`を要求し、値が一致しなければ例外を投げる。コンテキスト側のファクトリメソッドだけがこの内部シンボルを知っている
  - **理由**: TypeScriptの`private`/`protected`コンストラクタは「別クラスであるコンテキストからだけ呼べるようにする」という今回の要件を素直には満たせない（別クラスからはアクセスできないため）。非公開シンボルをブランドとして使う方式なら、型レベル（シンボルの型が外部から作れない）と実行時レベル（実際の値が外部から取得できない）の両方で`new User()`の直接呼び出しを防げる。数行で実装でき、「明示性を優先・実装コストを抑える」という全体方針にも合う
  - **割り切り**: 完全に破られない保証はない（リフレクション等で理論上は迂回可能）が、そこまでの堅牢性は今回不要と判断
- **エスケープハッチ**: 用意する。`context.raw`（仮称）として、コンテキストが内部で保持しているdrizzleの`db`/`tx`ハンドルをそのまま公開する方式を採用
  - **理由**: 9章の調査通り、Model API単体で表現しきれないクエリ（集計・サブクエリ・複数hasMany同時取得など）のためにSQL-first志向のユーザーを取りこぼさないために必要。「Drizzleは永続化エンジン」原則からしても隠蔽しきる理由がない
  - **トランザクション整合性**: コンテキストがすでに自分の`db`/`tx`ハンドルを保持している設計（コンストラクタ注入の決定）なので、それをそのまま公開するだけで済み、追加の配線は不要。トランザクション中のコンテキスト（`context.transaction(async (txContext) => {...})`内）であれば、`txContext.raw`は自動的にそのトランザクションの`tx`を指す
  - **戻り値**: `context.raw`経由のクエリ結果はModelインスタンスへhydrateせず、drizzleのプレーンな結果のまま返す。任意の集計・複数テーブルをまたぐ結果をModelクラスに対応付ける汎用的な仕組みは実装コストが見合わないため、「エスケープハッチを使う＝Model層の外に出る」と割り切る
- **TCP系/HTTP系ドライバ両対応の詳細**: Model層は特定のドライバを意識するコードを一切持たず、「すでに構成済みのdrizzleの`db`インスタンスを受け取るだけ」という方式で対応する
  - **理由**: Drizzle自体がすでにdialectごとに複数のドライバアダプタ（Postgres: `node-postgres`/`postgres-js`（TCP）、`neon-http`（HTTP）等。MySQL: `mysql2`（TCP）。SQLite: `better-sqlite3`（ローカル）、`d1`（Cloudflare D1）、`libsql`（HTTP）等）を提供しており、各dialect内で`db`のインターフェース（select/insert/update/deleteのビルダーメソッド）を統一している。ユーザーは自分の環境（Railwayならnode-postgres、D1ならdrizzle-orm/d1等）に応じてdrizzle公式ドキュメント通りにドライバを選び、出来上がった`db`をコンテキストのファクトリ（`createContext(db, schema)`的なもの）に渡すだけでよく、Model層側にドライバ別の分岐コードは不要
  - **既知の注意点**: HTTPベースのドライバ（`neon-http`、D1の一部モード等）はTCP系ドライバに比べてトランザクションのサポートが限定的（インタラクティブなトランザクションが使えずバッチ実行のみ、等）というdrizzle側の既知の制約がある。次のトランザクション設計の決定でこの制約を踏まえている
- **対応ランタイム（優先度）**: Node.js・Cloudflare Workers・Bunの3つを対応対象とする。Denoは今回は対象外
  - **理由**: Node.jsはRailway等の標準ホスティング、Cloudflare WorkersはD1利用を見据えてすでに前提になっていた。加えて本人が普段Bunを使っており（Honoと組み合わせて使用、今後Elysia等の他のBunネイティブフレームワークでの利用も見込む）、実際に自分が使うランタイムとして明確に対応範囲に入れる
- **モジュール形式**: ESM-only。CJS（CommonJS）には対応しない
  - **理由**: Node.js・Bun・Cloudflare Workersのいずれも現在ではESMを標準的に扱え、対応対象ランタイムの中に古いCJS前提の環境を残す必要がない。個人利用のプロジェクトであり、わざわざ廃れつつあるCJSへの互換対応コストをかける理由がないという判断。（better-drizzleはESM/CJS両対応のdual packageだが、そちらとの差分として許容する）
- **バリデーション統合方針**: zodを利用する。同期的な形式チェック（型・必須・長さ等）はModel定義側にzodスキーマを持たせる形（`static schema`的なもの）で対応し、DB問い合わせが必要な非同期バリデーション（ユニーク制約チェック等）は別途フック（`beforeCreate`等、contextにアクセスできる関数）側で対応する、というハイブリッド方式を採用
  - **理由**: drizzle-zodでdrizzleのテーブル定義からzodスキーマを自動生成できるため、生成したスキーマをModel定義に紐付けるだけで済み実装コストが低い。またModelクラスを見ればバリデーションルールがそこにあるという一体感があり、EF CoreのData Annotationsに近い書き味になる。一方でDB問い合わせを伴う非同期バリデーションは静的なスキーマ宣言だけでは表現できないため、contextにアクセスできるフック側に切り出す
- **フック失敗時の挙動**: フック（`beforeCreate`等の非同期バリデーションフックを含む）が失敗した場合は、例外を投げてDB操作（該当のCRUD呼び出し）を停止させる方式を採用。結果オブジェクトを返して処理を継続させる方式は採らない
  - **理由**: 「明示性を優先する」原則と合う。失敗を握りつぶさず即座に例外として伝播させることで、呼び出し側が失敗を見落とさずに済む。また`user.save()`が呼んだ瞬間に即時反映される設計（自動Change Trackingなし）とも整合し、フック失敗時に「一部だけ実行された」曖昧な状態を残さず、そのCRUD呼び出し自体をなかったことにできる
- **クエリ結果のバリデーション**: 行う方針とし、ツールは書き込み側と同じzod（drizzle-zodで生成したスキーマを再利用）とする。実行タイミングは、本番/開発/テストで分岐する専用フラグは用意せず、Model層の翻訳パイプライン（drizzleのSELECT結果をModelインスタンスへhydrateする処理）に常に組み込まれた処理として扱う（結果として常時実行になる）
  - **経緯**: 当初はAjv/TypeBoxのようなコンパイル型バリデータへの乗り換えや、Valibotのような軽量ライブラリへの乗り換えも検討したが、「ツール（ライブラリ）を変えても1件あたりの検証コストの本質は変わらない」という判断から、ツール選定ではなく実行の仕組み側でオーバーヘッドを抑える方針に切り替えた
  - **仕組み**: Model定義（クラス登録）のタイミングで、そのテーブル用の検証関数を1回だけ組み立てておく（毎クエリでスキーマをたどり直さない）。drizzleのSELECTが返した生の行データを、Model層側でhydrateする前にその検証関数へ通す。drizzle自体には検証を組み込む機構がないため、drizzleに何かを渡すのではなく、Model層の既存のクエリパイプラインに1段挟む形にする（「drizzleは永続化エンジンに徹する」原則と一貫）
  - **本番実行タイミングの決着**: 「本番でも常時実行するか、開発・テスト時限定にするか」は、環境ごとに分岐するモード/フラグを別途作らず、検証をパイプラインの固定された一部として常に動かす形で決着した。これにより「本番だけ無効化する」という設定項目自体を持たずに済み、実装コスト・設定の複雑さを抑えられる（「実装コストを抑える」原則と一貫）。一方で、この選択は「本番で発生したスキーマドリフト（マイグレーション未適用、DB外からの直接変更等）が即座に例外として表面化する」というfail-fastな挙動を受け入れることも意味する。すでに「フック失敗時は例外を投げて操作を停止する」方針と一貫しており、データを黙って壊れたまま返すよりは失敗を明示する方を優先する、という全体方針とも整合する
  - **失敗時の挙動**: フック失敗時と同様、例外を投げてDB操作を停止させる
- **タイムスタンプ自動管理**: `createdAt`/`updatedAt`は、Model層のフックやCRUD変換パイプラインには手を入れず、drizzleの列定義（`pgTable`等）内でそのまま使う専用ヘルパー関数（`createdAtColumn()` / `updatedAtColumn()`、仮称）として提供する方式を採用
  - **理由**: EF Coreのようなconvention/SaveChanges Interceptorベースの自動付与は、すでに不採用と決めた「自動Change Tracking」路線に寄ってしまい、このORMの「明示性を優先する」原則とも噛み合わない。ヘルパー関数はdrizzle自身が持つカラムレベルの機構（`defaultNow()`、`$onUpdate(() => new Date())`等）を薄くラップするだけなので、Model層のフックや`.save()`のパイプラインを経由せず、値の設定自体をdrizzle（永続化エンジン側）にそのまま委譲できる。「スキーマ定義はユーザーがdrizzleの`pgTable`を直接書く」という既存決定とも一貫し（別DSLではなく`pgTable`の中で使う一部品）、実装コストも低い
  - **実装時の注意点**: `defaultNow()`/`$onUpdate()`の具体的な書き方はdialectごとに差がある（PostgreSQL/MySQLはSQL関数、SQLiteは`unixepoch()`等）ため、`createdAtColumn()`/`updatedAtColumn()`ヘルパー内でdialectごとの分岐を吸収する必要がある
- **シリアライズ／`toJSON`**: Model層は何も提供せず、標準のJSクラスの`toJSON()` override機構にそのまま委ねる方針を採用
  - **理由**: すでに決定済みの設計（コンテキスト参照はコンストラクタ注入によりprivateフィールド`#context`として保持）により、`JSON.stringify(user)`を素朴に呼んでもprivateフィールドはJSエンジンの組み込み挙動として列挙対象から自動的に除外されるため、内部状態が漏れる問題は追加対策なしにすでに解消されている。カラムの値はインスタンスの列挙可能プロパティとして持つ設計になるため`JSON.stringify`はそのまま素直に効き、タイムスタンプ等の`Date`も標準の`toJSON()`によりISO文字列化される。パスワードハッシュ等の除外やキー名変換が必要な場合は、JSの標準機能としてユーザー自身がModelクラスに`toJSON()`をoverrideすればよく、ORM側が別途機構を用意する必要はない
  - **オーバーヘッドの観点**: overrideに委ねる方式はユーザーが書いたコード以外に何も挟まらないため、選択肢の中で最もオーバーヘッドが小さい（ほぼゼロ）。逆に、除外フィールド宣言のような汎用機構をORM側に用意した場合は、毎回のシリアライズ時に宣言内容と照合しながらプロパティを走査する処理が挟まり、overrideより重くなる（クエリ結果バリデーションでの「汎用化するほど1回あたりのコストが上がる」という論点と同型）
  - **全体方針との整合**: 「実装コストを抑える」「明示性を優先する」という全体方針とも一貫する
- **継承・Mixin**: 複数階層にまたがる`is-a`継承（例: `class Employee extends Person`のような多段クラス階層）を積極的に使わせる設計はせず、機能単位で独立したmixin関数（クラスを受け取りクラスを返す関数。例: `class Post extends SoftDeletable(Timestamped(Model)) {}`）による合成寄りのアーキテクチャを採用する
  - **経緯**: EF Coreのエンティティは実際にはpublicなgetter/setterのみを持つ薄いデータの入れ物で、賢い処理（クエリ・変更検知等）はDbContext側にあり、深いOOP的継承には依存していない。このORMも同様に、CRUD変換・hydration・バリデーションのパイプラインはModel本体ではなくContext側にあるため、Modelクラス自体はもともと薄い（カラムの値＋`save()`/`update()`/`delete()`/`reload()`程度）。この形は「本当のhas-a合成」（別オブジェクトを保持して委譲する形）とは相性が悪い（`delete()`等の既存メソッドの挙動そのものに割り込む必要があるため）一方、mixin関数によるクラス合成とは相性が良い
  - **理由**: ソフトデリート・名前付きスコープのような横断的機能を、独立したmixin関数として実装し、必要なものだけ組み合わせて使ってもらう形にできる。ブランドSymbol・`#context`まわりの配線は各mixin関数内で一度だけ面倒を見ればよく、利用者は気にしなくて済む
  - **DBスキーマレベルの継承（TPH/TPT/TPC等）とは別軸**: EF Coreの`OnModelCreating(modelBuilder)`のようなテーブルマッピング戦略の設定は、すでに決定済みの「スキーマ定義はユーザーがdrizzleの`pgTable`を直接書く、Model層に別DSLは持たせない」という原則の対象であり、Model層に専用のbuilder関数は用意しない。テーブル分割・discriminator列等はユーザーが`pgTable`側で表現し、Model側は`static table`の紐付けで対応する
- **ソフトデリート**: `deletedAtColumn()`（仮称、nullableなタイムスタンプカラム用ヘルパー）をユーザーが自分の`pgTable`に追加し、`SoftDeletable`ミックスイン（`class Post extends SoftDeletable(Model) {}`）を明示的に適用したModelだけソフトデリート対応にする方式を採用。ハード削除（実際の`DELETE`）とソフトデリート（`deletedAt`への`UPDATE`）を両方使えるようにする
  - **理由**: 「スキーマ定義はユーザーが`pgTable`を直接書く」「継承・Mixinはmixin関数による合成」というすでに決定済みの2つの方針とそのまま合流する形。カラム名（例: `deletedAt`という名前）だけを見て自動判定するconvention方式は取らず、Mixinを明示適用したかどうかで判定するため、暗黙の魔法を持ち込まずに済む。Mixinを適用しなければ`.delete()`は従来通りハード削除のまま
  - **クエリの自動除外（グローバルクエリフィルタ）**: `SoftDeletable`を適用したModelに限り、通常の`find()`等のクエリ経路もそのMixinが上書きし、デフォルトでソフトデリート済みの行を自動的に除外する。削除済みの行も見たい場合は`withDeleted()`（仮称）のような形で明示的に含める
  - **明示性原則との整合**: 「素の`find()`が暗黙に一部の行を隠す」という暗黙動作自体は認めつつ、それが発生する範囲を「`SoftDeletable`を明示的に選んだModelの中だけ」に閉じ込めることで、全体としての「明示性を優先する」原則とは矛盾しないと整理した。自動除外なしの案は原則には忠実だが、呼び出し側が`deletedAt`条件を書き忘れて削除済み行が漏れて表示される事故が起きやすく、ソフトデリート機能としての実用性を優先した
- **名前付きスコープ**: 専用機能としては用意しない。ユーザーが自分で「条件オブジェクト（または条件を返す関数）」を定義し、`context.users.find()`等に渡す形で十分とする
  - **理由**: EF Coreも「名前付きスコープ」に相当する専用機能を持たず、`IQueryable`に対する拡張メソッド（クエリを受け取ってクエリを返す関数）をユーザーが自分で書くだけで同じことを実現している。これはC#のLINQ/`IQueryable`がそもそも合成可能な値であることに支えられている。TypeScript側でも、`context.users.find()`が受け取る`where`条件はプレーンなオブジェクト（またはdrizzleのクエリ条件相当の値）になる想定のため、同じ構図がそのまま成り立つ。例: `const activeUsers = () => ({ where: { isActive: true } }); context.users.find(activeUsers());`
  - **既存決定との整合**: `toJSON`はJSの標準override、タイムスタンプはdrizzleのカラム機構に委ねたのと同じく、「言語やdrizzle側にすでに十分な表現力があるなら、ORM側で専用DSLを追加で作らない」という一貫した考え方に基づく。ソフトデリートのMixinとは異なり、既存メソッドの挙動に割り込む必要がなく、単なる再利用可能な条件でしかないため、専用機構を持たない判断がそのまま成り立つ
- **トランザクションとコンテキストの対応関係**: 以下の形で整理して決定
  - **API形状**: drizzleの`db.transaction(async tx => {...})`と同じコールバック型で、`context.transaction(async (txContext) => {...})`のように、コールバック内で専用のtxContext（トランザクション用の別コンテキストインスタンス）を受け取る形にする
  - **既存Modelインスタンスの扱い**: 「Modelインスタンスは生成時のコンテキストに固定（Attach的な後付け紐付けをしない）」という既存決定の直接の帰結として、トランザクション外で取得済みのModelインスタンスはトランザクション内で使ってもそのトランザクションには参加しない。トランザクション内で操作したいものは`txContext`側で改めて取得し直す必要がある、という制約として明示的に受け入れる
  - **ネストしたトランザクション**: 対応する。drizzle自体がTCP系ドライバでSAVEPOINTベースのネストしたトランザクション（`tx.transaction(...)`）に対応しているため、それを踏襲する
  - **afterCommit/afterRollbackコールバック**: 初期スコープに含める。txContext側にコールバックのリストを持たせ、commit/rollback後に呼び出す形。明示的に登録する形にできるため実装コストが低く、「明示性を優先する」原則にも合う
  - **リトライ機構**: 初期スコープからは見送り、将来課題として保留。デッドロック等の一時的な失敗の検知・リトライはエラー種別がDB dialectごとに異なり、冪等性の考慮も必要になるため実装コストが高く、楽観的排他制御と同様の扱いとする（詳細・代替案は7章参照）
  - **HTTPドライバの制約**: neon-http・D1の一部モード等のインタラクティブなトランザクションが使えないドライバでの`context.transaction()`の挙動（エラーにするか等）は、実装時に個別に詰める
- **スキーマ定義をユーザーにどこまで見せるか**: ユーザーがdrizzleの`pgTable`等のテーブル定義を直接書く前提とする（Model層側で隠蔽・別DSL化はしない）
  - **理由**: すでに決定済みの「Fluent API/Data Annotations的なスキーマ設定はModel層に持たせない」という方針とも一貫する。「明示性を優先する」原則、および「ORMとしての魔法を作りたいわけではない」という本人の方針からも、drizzleのテーブル定義をそのまま見せることに問題はない
  - **Modelクラスとの紐付け方**: `class User extends Model { static table = usersTable }`のように、drizzleのテーブル定義オブジェクトをModelクラスの静的プロパティとして持たせる形で紐付ける
- **パフォーマンスオーバーヘッドの比較対象**: 生drizzleそのものではなく、Prismaなど「翻訳層を挟むORM」を比較対象に置く
  - **理由**: Model層はdrizzleの上にCRUD・アソシエーション・バリデーション等の翻訳層を被せる構成である以上、生drizzleに対して性能で劣るのは避けられない当然の前提と捉える。数値目標を立てるなら、同じく翻訳層を挟むPrisma等の既存ORMと比べて明らかに見劣りしない程度を目安とする方が妥当
- **型チェック速度への向き合い方**: 設計段階から意識する方針とする
  - **理由**: 現時点では個人利用目的だが、本人としては将来的にOSS化する可能性も考えている（7章の「他人への配布・OSS化」参照：実装完了後にGitHub公開する計画がある）。他人が使う可能性が残る以上、過度に深いジェネリクスの積み重ね等でtsserver/tscが重くなる事態は、問題が出てから対処するのではなく早い段階から避けておく方針とする。具体的な設計上の制約（型の重さの許容ライン等）は実装時に個別に詰める
- **バンドルサイズの目標**: Cloudflare Workersのデプロイ制約を目安にする。理想は無料枠の1MB（gzip後）以内、それが難しくても有料枠の10MB以内には収める、という目標値を設定する
  - **理由**: 小規模用途でもWorkers上で問題なく動かせる状態を維持したいため、Workersの実際の制約をそのままバンドルサイズの目安として採用する。加えて、drizzleをベースにしている以上、フルスタックのPrismaほどバンドルが重くなることはないだろう、という見立てがある（本人談。実測での検証はまだ）。ただし6章のPrisma調査の通り、Prisma自体も2025年11月のv7でバンドルサイズを大幅に削減してきているため、この見立ての妥当性は実装後のベンチマークで改めて確認する必要がある
- **テスト方針：実DBの用意の仕方**: 実DBに対するテストは、永続的な開発用DBではなく、テスト実行のたびに使い捨てのコンテナ（Docker等）で起動して破棄する方式を採用
  - **理由**: 毎回まっさらな状態からテストを始められるため、テストの独立性・再現性が保ちやすい。個人開発でもコンテナさえ起動できればセットアップの手間はさほど大きくない
- **テスト方針：実DBでカバーする範囲**: SQLite in-memoryへの切り分けはせず、テスト全体を実DB（使い捨てコンテナ）で実行する方針に決定
  - **理由**: コンテナの起動・破棄はテストケースごとではなくテストスイート全体で1回に抑えられるため、対象範囲を広げても起動コストはさほど増えない。増分は各テストが実DBに対して実際にクエリを打つ実行時間のみで、個人開発の規模なら許容範囲と判断した。加えて、SQLite in-memoryと実DBの2系統のテストコードを持たずに済み、PostgreSQL/MySQL/SQLite間のdialect差（型の扱い、SAVEPOINTの有無等）を全テストで自然に拾えるようになる
- **テスト方針：テストランナー**: `bun test`を採用
  - **理由**: 対応ランタイムの一つとしてすでにBunを選んでおり、本人も普段Bunを使っている。`bun test`ならBunさえ入っていれば追加の依存なしで動き、Jest互換APIでcoverage/watch/snapshotも一通り揃っている。個人開発でツールを増やしたくない、という文脈にも合う。Vitestの方がCloudflare Workersのランタイム内テスト（`@cloudflare/vitest-pool-workers`）に強みがあるが、今回のテストの主眼はhydration/トランザクションといったDBレベルの正しさであり、その強みは現時点では重要度が低いと判断。加えて`bun test`自体もそれなりに使われており、実用に耐えないツールではないという点も後押しした
- **テスト方針：CI導入**: 導入する。ツールはGitHub Actions、実行タイミングは`push`イベント（全ブランチ、`pull_request`トリガーとの併用はしない）とする
  - **理由**: 実DBがすでに使い捨てコンテナ前提のため、GitHub Actionsのservice containers等でPostgreSQL/MySQLを立てるだけで済み（SQLiteはコンテナ不要）、導入コストは小さい。1章に残る「drizzle-ormの破壊的変更への追従方針」に対しても、依存更新時に機械的に検知できる保険になる
  - **実行タイミングの理由**: 開発中でも壊れたタイミングをすぐ把握したい、という要望から`push`時に実行する方針とした。PRを必ず使う運用にするかは未確定（使うかどうかは開発者自身の裁量）だが、`push`のみをトリガーにしておけば、PR経由でも直push運用でもどちらでも自然にカバーされ、`push`と`pull_request`を両方トリガーにした場合に起きがちな「PRマージ時の二重実行」も避けられる。ブランチを絞らない`push`トリガーにしておけば、Dependabotが作成するブランチへのpushも同じ仕組みで拾えるため、「drizzle-ormの破壊的変更を依存更新時に検知する」という導入理由ともDependabot運用を組み合わせれば自然に噛み合う
  - **将来的な最適化として保留**: 実DBコンテナ起動を伴うため1回の実行コストは軽くなく、README等のコード非依存の変更にまでフルテストを毎回走らせるのは無駄になりやすい。`paths-ignore`や`[skip ci]`によるスキップは有効な最適化だが、今回は方針決定のみで、導入自体は必須事項とはせず後から追加できるものとして保留する
- **drizzle初期化時の設定項目の削減**: 「Modelにした場合すでに決まっていることをdrizzle側で設定し直す」重複を避け、実質的にDB接続情報だけ渡せば済む状態を目指す方向で整理
  - **schema**: 渡さない。`db.query`（relational query API）を使わない方針（リレーションはModel層/DbContext側で扱う。決定事項セクション参照）のため、drizzle初期化（`drizzle(connection, {...})`）に`schema`を渡す理由がない。コンテキストファクトリ側（`createContext(db, schema)`仮称）が使う「Model一覧」とは別物であり、そちらは引き続き必要
  - **casing**: `casing: 'snake_case'`のような自動変換オプションは使わない。カラム命名は原則camelCaseに統一し、`pgTable`側の物理カラム名もそのままcamelCaseで書かせる前提とする
    - **理由**: bool型カラムをsnake_case＋casing変換で扱う際にTypeScript側の型推論まわりで問題が絡んでくる（本人の実体験）ため、変換機構自体を使わない方が安全。変換オプションを使わなければユーザーがcasingを意識して設定する作業自体もなくなる
  - **logger**: オプション自体は残すが、初期値としてoffをデフォルトにしてORM側で内蔵しておき、変更したい人だけ上書きすればいい仕様にする方針
    - **デフォルト値の決着**: off。drizzle自体のデフォルト（logger未指定＝無効）と揃えることで、「オプションを何も指定しなければ生drizzleと同じ挙動になる」という薄いラッパーとしての一貫性を保てる。加えて、onをデフォルトにした場合の事故（本番で気づかずクエリログを垂れ流す、Cloudflare Workersでのログ出力コスト・ボリューム増、パラメータ実値の意図しない露出等）の方が、offをデフォルトにした場合の不便（開発時に明示的にonにし忘れる）より被害が大きいと判断した
- **drizzle-ormの破壊的変更への追従方針**: 「バージョンは即座に追従する」「メジャーアップデートは必ず手動レビューする」のような固定的なルールを事前に作り込むのではなく、都度の変更内容を見て判断する運用スタンスとする
  - **経緯・調査**: 実際に調べたところ、drizzle-ormはv0系（安定版）からv1系への移行が進行中で、v1では`casing`オプションのスキーマ定義側APIへの移行、`db.query`（Relational Queries）のv2（`defineRelations()`）への刷新、drizzle-zod等バリデーションパッケージのコア統合、マイグレーションのフォルダ構造刷新など、比較的大きめの書き方変更が入る見込み。ただし今回すでに「`db.query`/`relations()`を使わない」「`casing`オプションを使わない」という設計にしているため、v1で最も破壊的な変更2つの影響はそもそも受けない。当面はv0系の安定版に留まり、v1が正式リリース（beta/rcの間は使わない）された後も、影響がなければ追従して構わない
  - **通常のアップデート**: CI（`push`時実行、決定事項セクション参照）を通過すれば、そのまま追従して問題ない
  - **利用箇所に影響する破壊的変更が来た場合**: 自動追従はせず、その都度「追従するかどうか」を個別に判断する
  - **drizzleの設計思想自体が変わった場合**: バージョン追従の是非を超えて、Model層が依存する永続化エンジンをdrizzleから乗り換える、という選択肢まで視野に入れる。drizzleに依存している以上避けられない構造的なリスクであり、v1の変更が無害でもv2・v3で同様の事態が起きうるため、特定バージョンの変更内容だけを見て安心できる話ではない
  - **結論**: 事前に細かい追従ルールを作り込むのではなく、drizzleの更新情報（リリースノート等）を継続的にウォッチしつつ、その都度対応していく運用とする

## 1. 「Drizzle互換」が指すものの切り分け（決定済み）

- **drizzle-kit（マイグレーション）との互換性**: drizzleにmigrationを担わせる
- **SQL生成・実行**: drizzleに担わせる（Model層はdrizzle呼び出しへの変換のみ）
- **クエリビルダAPIの互換性（書き込み側）**（大枠）: Model層がdrizzleの呼び出しに変換する形
- **リレーション定義**: Model層で定義し、drizzleへの呼び出しに変換する
- **リレーションの変換先**: 親キーのIN句によるバッチクエリ＋アプリ側hydration方式（決定事項セクション参照）
- **ドライバ／dialect互換性**: Model層はdrizzleの`db`インスタンスを受け取るだけで、ドライバ別の分岐コードは持たない（決定事項セクション参照）
- **エスケープハッチ**: `context.raw`でdrizzleハンドルを直接公開（決定事項セクション参照）
- **スキーマ定義の互換性**: `pgTable`等のdrizzleのテーブル定義関数・型をそのまま使う（決定事項セクション参照）
- 型推論の互換性: drizzleの推論型（`InferSelectModel` / `InferInsertModel`）をModel APIの型としてそのまま採用する方向で概ね解決見込み（CRUD側）。ただしリレーション結果のネスト型は自前で組み立てる必要がある
- **drizzle-ormの破壊的変更への追従方針**: 固定ルールは定めず、CIを通過する通常アップデートはそのまま追従、利用箇所に影響する変更は都度判断、drizzleの設計思想自体が変わる場合は永続化エンジンの乗り換えも視野に入れつつ、更新情報を継続的にウォッチして保守していく（決定事項セクション参照）

1章はこれで決定事項が出揃った。

## 2. Model層に求める機能候補（決定済み）

- **インスタンスメソッド**: `user.save()` / `user.update()` / `user.delete()` / `user.reload()` などを持たせる（内部でdrizzleのUPDATE/DELETE/SELECTに変換。呼んだ瞬間に即時反映、自動Change Trackingはしない）
- **コンテキスト経由のCRUD**: `context.users.find()` / `context.users.add()` のようなDbContext的な入り口も持たせる（インスタンスメソッドと併用）
- **アソシエーションのネスト対応範囲・hydration設計**: 1段階まで（あえて維持）、リレーションごとにIN句のバッチクエリ＋アプリ側マージ、hydrationは親主キーでのgroupBy（決定事項セクション参照）
- **エスケープハッチ**: `context.raw`（決定事項セクション参照）
- **バリデーション（zod連携か独自機構か）**: zod連携。同期チェックはModel定義側にスキーマを持たせ、非同期チェックはフック側（決定事項セクション参照）
- **変換前にフック/バリデーションを挟む位置**: 非同期バリデーション（ユニーク制約チェック等）は`beforeCreate`等のフックとして、drizzle呼び出しへの変換の前段に挟む。フック失敗時は例外を投げてDB操作を停止させる（決定事項セクション参照）
- **トランザクション・スコープ管理**: `context.transaction(async (txContext) => {...})`形式、ネスト対応、afterCommit/afterRollbackコールバック対応、リトライ機構は将来課題として保留（決定事項セクション参照）
- **better-drizzleとの差別化**: クラスベース＋インスタンスメソッド＋DbContext的なAPI表面の書き味の違いですでに十分（決定事項セクション参照）。drizzle自体に対してユーザーが設定する項目数を減らす方向性は、差別化目的ではなく独立した使いやすさ向上のアイデアとして着手し、schema/casing/loggerデフォルト値まで含めて決定済み（決定事項セクション参照）
- **クエリ結果のバリデーション**: zod（drizzle-zodのスキーマを再利用）で行う。Model定義時に検証関数を1回だけ組み立て、drizzleのSELECT結果をhydrate前にModel層のパイプライン内で検証、失敗時は例外で停止。実行タイミングは本番/開発/テストで分岐させず、翻訳パイプラインの固定された一部として常時実行する（決定事項セクション参照）
- **タイムスタンプ自動管理**: EF Core的な自動convention/Interceptorには寄せず、`createdAtColumn()`/`updatedAtColumn()`ヘルパー関数を`pgTable`内で使う形にする。drizzleの`defaultNow()`/`$onUpdate()`を薄くラップし、Model層のフックや`.save()`パイプラインは経由しない（決定事項セクション参照）
- **シリアライズ／`toJSON`**: Model層は何も提供せず、標準のJSクラスの`toJSON()` override機構に委ねる。privateフィールドは元々JSONに含まれないため追加対策不要、除外・キー変換等が必要ならユーザーがModelクラスに`toJSON()`をoverrideする（決定事項セクション参照）
- **継承・Mixinの可否**: 多段の`is-a`継承は積極利用させず、機能単位のmixin関数（クラスを受け取りクラスを返す関数）による合成寄りのアーキテクチャを採用。DBスキーマレベルの継承（TPH/TPT/TPC等）はModel層のbuilder DSLではなく`pgTable`側で表現する（決定事項セクション参照）
- **ソフトデリート**: `deletedAtColumn()`ヘルパー＋`SoftDeletable`ミックスインを明示適用したModelのみ対応。ハード削除・ソフトデリート両対応。`SoftDeletable`適用Modelは通常のクエリでソフトデリート済み行をデフォルト除外し、`withDeleted()`等で明示的に含める（決定事項セクション参照）
- **名前付きスコープ**: 専用機能は用意しない。EF Coreが`IQueryable`拡張メソッドで代替しているのと同じく、ユーザーが自分で条件オブジェクト/関数を定義して`find()`等に渡せば十分（決定事項セクション参照）

2章はこれで決定事項が出揃った。

## 6. 参考にする既存実装（比較用メモ）

- Sequelize / TypeORM / Prisma（Node.js勢。TypeORMは利用者が少なそうなため優先度低め）
- Objection.js / Bookshelf.js（knexベース。クエリビルダをラップしてModel層を被せる構成の先例として参考になりそう）
- ActiveRecord（Rails）/ Eloquent（Laravel）
- EF Core（本人が馴染みがある。移植範囲は決定事項セクション参照。DbContext・ナビゲーションプロパティ・Fluent APIの考え方は反映済み、Lazy Loading・自動Change Trackingは不採用）
- **better-drizzle**（[GitHub](https://github.com/almeidazs/better-drizzle) / [公式サイト](https://better-drizzle.com/)）: 実際のソースコード（`packages/core/src/shared/client/`配下）を読んで比較した。version 0.1.1時点でのメモ
  - **API形**: `const client = better(db, { schema })` でラップし、`client.user.findMany(...)` のようにテーブルごとのデリゲートオブジェクト（コンテキスト的な入り口）経由で操作する関数/ファクトリベースのリポジトリスタイル。`post.save()`のようなインスタンスメソッドは持たない（今回はクラスベース＋インスタンスメソッドを持たせる方針で意図的に差別化）
  - **CRUD**: `findMany`/`findFirst`/`create`/`createMany`/`update`/`updateMany`/`updateEach`/`upsert`/`upsertMany`/`delete`/`deleteMany`/`exists`等、非常に幅広い統一メソッド群をテーブルごとに提供
  - **リレーションのeager loading（実装の核心）**: JOINはほぼ使わない。`include`で複数リレーションを取得する場合、リレーションごとに親のキー配列を`IN`句にした別クエリを1本発行し、アプリ側で親キーごとにgroupByしてhydrateするバッチクエリ方式（`loadRelation`/`hydrateRelations`）。この方式は再帰的に呼ばれるため多段ネストにも自然に対応している。JOINを使うのは「単一の`belongsTo`（One）リレーションをフィルタ条件に使う」特殊ケース（`where: { author: { is: {...} } }`）のみ。さらに、このバッチクエリ方式や特殊JOINでも表現できない複雑なクエリ（列選択と複数リレーション混在等）では、drizzleの`db.query`（relational query API）そのものにフォールバックする実装になっている
  - **今回の設計への影響**: この調査結果を受けて、リレーションの変換先を「select+join」から「親キーのIN句によるバッチクエリ＋アプリ側hydration」に変更した（決定事項セクション参照）。JOINをやめたことで、fan-out問題が原理的に発生しなくなり、多段ネストも技術的には無理なく対応できるようになったが、初期スコープでは「1段階まで」の制約をあえて残している
  - **マイグレーション**: リポジトリ内に専用の記載はなく、drizzle-kit依存と推測
  - **トランザクション**: ネストしたトランザクション（SQLiteはSAVEPOINTを明示的に発行、他ダイアレクトはdrizzleのネストしたトランザクションに委譲）、opt-inのリトライ（deadlock/serializationFailure/connectionErrorを判別し、遅延関数も設定可）、`afterCommit`/`afterRollback`コールバック、AbortSignal/timeoutによる中断まで対応。今回「ネスト対応・afterCommit/afterRollback対応・リトライは保留」と決めた内容と方向性は一致しており、リトライの実装コストの高さもこの実装量から裏付けられた
  - **バリデーション**: 汎用プラグインアーキテクチャ（`definePlugin`。beforeCreate/afterCreate/beforeUpdate/afterUpdate/beforeQuery/afterQuery等のフック）上にzodプラグインが乗っており、drizzleのテーブル定義からzodスキーマを自動生成して使う点は今回の方針と一致。書き込み前だけでなく、クエリ結果（afterQuery/afterCreate等）も検証できるオプションを持っている点は、今回のクエリ結果バリデーションの決定（決定事項セクション参照）の着想元にもなった
  - **エスケープハッチ**: `$raw`/`$executeRaw`/`$rawUnsafe`の3メソッドに分かれており、`allowUnsafe`フラグでプレースホルダなしの生SQLだけ明示的にオプトインさせる安全策がある。今回の`context.raw`は単一のハンドル公開なので、この粒度分けまではやらない方針
  - **モジュール形式**: ESM/CJS両対応のdual package（`exports`でimport/require双方に対応）。今回はESM-onlyで決定済みなので、ここは意図的な差分として許容する
  - **対応DB**: PostgreSQL/SQLite/MySQL。コード生成・ビルドステップなし（0 codegen）
  - **差別化の論点**: クエリ戦略（バッチクエリ方式）自体はbetter-drizzleとかなり近くなったが、クラスベース＋インスタンスメソッド＋DbContext的なAPI表面という書き味の違いだけで差別化としては十分、と結論づけた（決定事項セクション参照）。「drizzle自体に対してユーザーが設定する項目数を減らす」方向性は、差別化のためではなく独立した使いやすさ向上のアイデアとして扱う（schema/casing/loggerデフォルト値まで決定済み。決定事項セクション参照）
- **Prisma**（[エッジ対応ドキュメント](https://www.prisma.io/docs/orm/prisma-client/deployment/edge/overview) / [Rust→TypeScript移行のブログ](https://www.prisma.io/blog/from-rust-to-typescript-a-new-chapter-for-prisma-orm) / [join戦略のブログ](https://www.prisma.io/blog/prisma-orm-now-lets-you-choose-the-best-join-strategy-preview)）: 本人が挙げた「一番の競合」として、書き味も含めて調査した。2025年11月〜2026年前半（Prisma v7前後）時点の情報
  - **API形/アーキテクチャ**: `.prisma`スキーマDSL＋`prisma generate`によるクライアント生成が必要（コード生成ステップあり）。drizzle・今回のORMのようなTypeScriptネイティブなスキーマ定義＋ゼロcodegenとは根本的に異なる。クエリAPIもSQLを抽象化した`findMany`/`create`のようなメソッドチェーンで、SQLライクな書き方（drizzleの`select().from().where()`）とは書き味の系統がそもそも違う。単純なAPI形の比較よりも、実装後のベンチマーク比較の方が実質的な意味を持ちそうという整理は妥当
  - **バンドルサイズ/アーキテクチャの変遷**: 元々Rustのネイティブクエリエンジンバイナリ（OSごと・OpenSSLバージョンごとに別バイナリが必要）をNode.jsプロセスから呼び出す構成で、パッケージサイズが約14MB（gzip後7MB）まで肥大化しており、コールドスタート増加やエッジランタイムでのネイティブバイナリ非対応といった問題があった。2025年11月のPrisma 7で「Query Compiler」というTypeScript/WASM構成に移行し、公称ではバンドルサイズが1.6MB（gzip後600KB）まで約85〜90%削減、クエリ性能も最大3.4倍向上したとされる
    - **注意点**: 「Rust-free」という表現は正確ではなく、WASM自体（2.4MB）はRustのコードをコンパイルしたものであり、実態は「ネイティブバイナリがなくなっただけ」に近いという指摘がある。完全にRustを介さない実行には有料のPrisma Accelerate（リモート実行サービス）が必要
    - この変遷を踏まえると、5章バンドルサイズの決定事項にある「drizzleベースの方がPrismaよりバンドルが軽いはず」という見立ては、Prisma側の急速な軽量化によって前提が揺らぎつつある。実装後のベンチマークで改めて実測比較する価値が高まった
  - **エッジランタイム対応**: Cloudflare Workers等で動かすには、TCP接続前提の標準ドライバではなく「Driver Adapters」（Neon Serverless、PlanetScale、Cloudflare D1向け等のHTTP/エッジ対応ドライバのアダプタ）が必要。TCP系ドライバ（`node-postgres`等）はCloudflare Workersでは動くがVercel Edge Functionsでは動かない、といった環境ごとの制約が残っている。今回のORMがすでに決定している「Model層はdrizzleの`db`インスタンスを受け取るだけ、ドライバ別分岐なし」（決定事項セクション参照）は、drizzle自体がドライバ差をすでに吸収している分、Prismaのこの複雑さとは対照的
  - **リレーションのフェッチ戦略**: Prisma 5.9.0より前は複数クエリ＋アプリ側マージの「query戦略」のみだったが、それ以降「join戦略」（lateral join＋DB側JSON集約で1回のラウンドトリップにまとめ、fan-outも回避する）がpreview機能として追加され、有効化するとjoinがデフォルトになる。fan-out回避という同じ課題に対して、今回のORMが選んだ「JOINを使わずIN句のバッチクエリ＋アプリ側hydration」（決定事項セクション参照）とは異なる解法（DB側のJSON集約機能に依存する解法）を取っている点が対照的。DB側JSON集約への対応度合いはdialectによって差が出やすく、PostgreSQL/MySQL/SQLite/D1という複数dialectをフラットに扱いたい今回の方針とは相性の面で違いが出やすいポイントと言える
  - **差別化の論点**: 書き方（API形）自体はSQLライクなdrizzleベースの設計とは系統が異なるため、機能比較よりも実装後のベンチマークで比較する方が実質的な意味を持つ、という整理はそのまま妥当。ただしバンドルサイズ・エッジランタイム対応はPrisma側が近年急速に改善してきている領域であり、「Prismaより軽いはず」という既存の見立ての妥当性を実測で検証する必要性が高まっている
- **実装後のベンチマーク比較の対象範囲**: ベンチマークを取るのは生drizzleとPrismaの2つのみとする（5章の決定事項と一致）。EF Coreは実行環境・言語（.NET/C# vs TypeScript）がそもそも異なりベンチマークでの直接比較が難しいため、ベンチマークは取らず、書き方（API形・DXの違い）を比較する形にとどめる。書き方の比較自体は決定事項セクションの随所（DbContext、ナビゲーションプロパティ、Fluent API等との対応関係）ですでに行っている。Sequelize/TypeORM/Objection.js/Bookshelf.js/ActiveRecord/Eloquentについては、参考リストとしてこのメモの記載で十分とし、これ以上の詳細な検証・ベンチマークは行わない

6章はこれで決定事項が出揃った。

## 7. 非目標候補（決定済み）

- **drizzleの全機能（view, materialized view等）を初期から網羅すること**（非目標）: 初期スコープでは網羅しない。実際に必要になった時点で都度追加していけばよいという判断
- **NoSQL対応**（非目標）: drizzle自体がSQL専用のORM/クエリビルダで、`pgTable`/`mysqlTable`/`sqliteTable`のようにリレーショナルDBのテーブル定義を前提にした設計になっており、MongoDBのようなNoSQLはそもそもdrizzleの対応範囲外。「drizzleを永続化エンジンとして扱う」というアーキテクチャ方針（決定事項セクション参照）とも矛盾するため、対応しない
- **他人への配布・OSS化**: 現時点では非目標のまま扱うが、恒久的な否定ではなく具体的な計画がある。まずは実装を一通り完成させることを最優先し、実装が形になった段階でGitHubに公開する予定。ドキュメント化は必須事項とはせず、公開後の状況次第で判断する（本人の周囲で使いたいという声が出るようであれば、その時点で早めにドキュメント化して公開する想定）。この将来のOSS化可能性は型チェック速度への向き合い方（決定事項セクション参照）にも影響しており、9章のようにユーザー像を調べること自体は設計の参考として継続中
- **EF Coreの`Attach()`的な、生成後の別コンテキスト/トランザクションへの再紐付け**（非目標）: Modelインスタンスは生成時のコンテキストに固定
- **遅延ロード（Lazy Loading）**（非目標）: Proxy不使用のため。eager loadingのみ対応
- **自動Change Tracking＋一括SaveChanges**（非目標）: 各インスタンスの変更は明示的な`.save()`等でのみ反映
- **楽観的排他制御（RowVersion的な同時更新検知）**（非目標）: 個人利用では優先度低く見送り（将来課題）。代替案として「アプリ側で直列処理する」も検討したが、対応ランタイムにCloudflare Workersを含む（決定事項セクション参照）ため複数isolate/instanceにまたがる直列化はそもそも現実的でなく、0章の「大規模までカバーしたい」という方針とも矛盾するため不採用。悲観的ロック（`SELECT ... FOR UPDATE`等）が必要な場面は、すでに用意している`context.raw`エスケープハッチ（決定事項セクション参照）でユーザー自身が書けば足りるため、ORM側に専用機構を持たせる必要はないと整理した
- **多段（孫関連以上）のネストしたeager loading**（非目標）: バッチクエリ方式への変更で技術的な制約はなくなったが、初期スコープを絞るためあえて1段階までに限定する（将来課題）
- **エスケープハッチ経由の結果を汎用的にModelへhydrateする仕組み**（非目標）: `context.raw`の結果はプレーンなdrizzle結果のまま
- **Model層独自のドライバ抽象化**（非目標）: drizzleの`db`インスタンスをそのまま受け取るだけ
- **Deno対応**（非目標）: 対応ランタイムはNode.js/Cloudflare Workers/Bunの3つに絞り、Denoは対象外
- **CommonJS (CJS) 対応**（非目標）: ESM-onlyとし、古いCJS環境への互換対応は行わない
- **トランザクションのリトライ機構**（非目標）: 楽観的排他制御と同様、デッドロック等のエラー種別がDB dialectごとに異なり、冪等性の考慮も必要になるため実装コストが高く、個人利用では優先度低く見送り（将来課題）。代替案は、ORM側に専用のリトライオプションを持たせるのではなく、`context.transaction(async (txContext) => {...})`が単なる非同期関数呼び出しである点を活かし、失敗時の例外を呼び出し元でtry/catchして`context.transaction()`を呼び直す、というユーザー側の通常のロジックで代替できると整理した。専用のリトライユーティリティを将来追加する余地は残すが、初期スコープでは不要と判断した
- **EF Coreのconvention/SaveChanges Interceptorベースのタイムスタンプ自動付与**（非目標）: `createdAtColumn()`/`updatedAtColumn()`ヘルパー＋drizzleのカラムレベル機構で代替（決定事項セクション参照）
- **ORM側による宣言的なJSONシリアライズ制御（除外フィールド指定等の専用機構）**（非目標）: 標準の`toJSON()` override機構に委ねる（決定事項セクション参照）
- **多段の`is-a`クラス継承を前提としたModel設計**（非目標）: 機能単位のmixin関数による合成を基本方針とする（決定事項セクション参照）
- **EF Coreの`modelBuilder`的な、Model層独自のテーブルマッピング/継承戦略DSL**（非目標）: `pgTable`側で表現し、Model層に専用DSLは持たせない（決定事項セクション参照）
- **カラム名によるソフトデリートの自動convention検出**（非目標）: `SoftDeletable`ミックスインの明示適用で判定する（決定事項セクション参照）
- **名前付きスコープの専用登録機構**（非目標）: ユーザー自身が条件オブジェクト/関数を定義すれば足りる（決定事項セクション参照）
- **クエリ結果バリデーションの本番/開発での有効・無効切り替え機構**（非目標）: 翻訳パイプラインの固定された一部として常時実行する（決定事項セクション参照）
- **drizzle初期化時の`schema`オプション指定**（非目標）: `db.query`を使わないため不要（決定事項セクション参照）
- **drizzle初期化時の`casing`変換オプション利用**（非目標）: camelCase統一とし、変換機構自体を使わない（決定事項セクション参照）
- **drizzle-ormのv1betaへの早期追従**（非目標）: 正式リリース前のbeta/rcは使わず、安定版に留まる（決定事項セクション参照）

7章はこれで全項目の確認が完了した。

## 9. ユーザー像の調査(誰がModelを求めているか・簡易リサーチ)

「Modelの概念が欲しい人はどういう人が多いか」について、軽く外部の実例を調べたメモ。継続して深掘りする余地あり。

- **欲しがる層の例**: 複数のエンティティ/テーブルを扱う中〜大規模プロジェクトのチーム開発者。ある技術リードは、NextJSプロジェクトで複数のサービスクラス間にCRUD処理（一覧取得・単体取得・削除・保存）が重複する課題感から、Drizzleに再利用可能なBase Serviceクラスを被せる実装をしていた。型安全性を保ちながら保守性を上げたい、という動機（[Supercharge Drizzle ORM with a Reusable Base Service Class](https://medium.com/@davxne/supercharge-drizzle-orm-with-a-reusable-base-service-class-86d01963d435)）
- **要らない・むしろ嫌う層の例**: レイテンシがシビアな本番環境（AI SaaS等）でPrismaからDrizzleに移行した開発者。Model/ActiveRecord的な抽象化がないこと自体を「クエリを隠さず書いている」利点として評価しており、SQLを恐れずパフォーマンスを最優先する層にはModel層はむしろ邪魔になりうる（[Drizzle ORM Is What Prisma Should Have Been](https://dev.to/whoffagents/drizzle-orm-is-what-prisma-should-have-been-a9j)）
- **既に近いことをやっている実例**: better-drizzle（6章参照）。「Drizzleを置き換えず薄くラップして、繰り返しのCRUDコードをなくす」というコンセプトは今回の方針と一致しており、この手のニーズが実際に存在することの裏付けになる
- **示唆**: Modelが刺さる層とSQL-first志向の層は割とはっきり分かれそうで、両方をある程度カバーするなら「Model層をデフォルトの入り口にしつつ、drizzleの生APIへ抜けられるエスケープハッチを用意する」設計が理にかなう。DbContext的な方針・エスケープハッチの重要度、どちらもこの調査結果と整合している
- **drizzle-ormのバージョニング状況（2026年8月時点の調査メモ）**: v0系（安定版、最新0.45.2）からv1系への移行が進行中で、2026年5月時点でv1.0.0-rc.3まで到達している。v1では`casing`のスキーマ定義側APIへの移行、`db.query`のv2（`defineRelations()`）への刷新、drizzle-zod等のコア統合、マイグレーションのフォルダ構造刷新などが予定されている。1章の「破壊的変更への追従方針」の決定に反映済み
- **本格的な調査開始タイミング**: 本格的なユーザー像調査はOSS公開後に着手する方針とする。実装が固まっていない現段階でこれ以上調べても仮説止まりになりやすく、OSS化して実際の利用者の反応が見えるタイミングで調査した方が、その後のドキュメント作成にも直接活きる。現時点ではまず実装を進めることが先決であり、9章の方向性はこれ以上具体化しない

9章は方針としてはこれで確定した（本格的な調査自体はOSS公開後に着手）。
